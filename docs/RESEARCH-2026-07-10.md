# Chrome WebDriver BiDi bootstrap research — 2026-07-10

## Executive conclusion

Chrome's extra WebDriver BiDi startup time is real, but it is not a WebDriver
BiDi protocol requirement. It is mostly the cost of creating a second hidden
renderer in which ChromeDriver runs the JavaScript BiDi-CDP Mapper.

On this Intel Mac, Chrome Stable 150 showed a **+430 ms median paired New
Session penalty** and a **+428 ms median paired post-boot penalty**. The browser
process boot itself was not the cause. Of the BiDi-only critical path:

| BiDi-only work | median | share |
|---|---:|---:|
| wait for hidden mapper renderer readiness | 266 ms | 62% |
| parse/evaluate the 830,648-byte mapper bundle | 61 ms | 14% |
| launch mapper instance | 29 ms | 7% |
| navigate the initial tab to `about:blank` | 25 ms | 6% |
| internal mapper `session.new` | 17 ms | 4% |
| runtime/CDP bridge and bindings | 15 ms | 4% |
| create and attach the hidden mapper target | 14 ms | 3% |

These medians total 427 ms. Component medians do not have to add exactly to the
median of paired totals, but here they closely match the measured 428 ms
post-boot delta.

The actionable conclusions are:

1. Making the mapper's JavaScript faster can recover only part of the penalty.
   The largest opportunity is eliminating, reusing, pre-warming, or changing
   the execution environment of the dedicated hidden renderer.
2. Chromium 152 still uses the same mapper architecture. It reduced some mapper
   phases in this run, but did not remove the per-session cost or make total
   startup faster.
3. The fastest fully fresh BiDi browser tested here was the supported standalone
   `chrome-headless-shell`: **998 ms BiDi vs 616 ms Classic**, still with a
   **382 ms mapper penalty**.
4. If process isolation per test is not required, keeping one BiDi session alive
   is substantially faster: a new isolated user context plus tab was ready in
   **406 ms median**, versus **2,426 ms** for the containing fresh Chrome BiDi
   session in that run.

## What Chrome actually does

The chromium-bidi project describes itself as a JavaScript layer that translates
BiDi and CDP and runs inside a Chrome tab. Chromium's own implementation guide
also says Chrome is controlled through CDP and ChromeDriver uses the mapper to
translate WebDriver BiDi commands into CDP commands.

Primary sources:

- [chromium-bidi README](https://github.com/GoogleChromeLabs/chromium-bidi#readme)
- [Chromium WebDriver BiDi implementation guide](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/testing/web_platform_tests.md#implement-webdriver-bidi-commands-using-cdp)
- [ChromeDriver M150 New Session implementation](https://chromium.googlesource.com/chromium/src/+/refs/branch-heads/7871/chrome/test/chromedriver/session_commands.cc#372)
- [ChromeDriver M150 mapper server setup](https://chromium.googlesource.com/chromium/src/+/refs/branch-heads/7871/chrome/test/chromedriver/chrome/devtools_client_impl.cc#302)
- [ChromeDriver M150 hidden-target implementation](https://chromium.googlesource.com/chromium/src/+/refs/branch-heads/7871/chrome/test/chromedriver/chrome/chrome_impl.cc#289)

The startup sequence when `webSocketUrl: true` is requested is synchronous:

```text
POST /session { webSocketUrl: true }
  -> launch Chrome and attach ChromeDriver to the initial target
  -> navigate the initial page to about:blank and wait
  -> Target.createTarget { url: "about:blank", hidden: true }
  -> discover, attach, initialize, and wait for that hidden renderer
  -> Target.exposeDevToolsProtocol as window.cdp
  -> Runtime.addBinding("sendBidiResponse")
  -> Runtime.addBinding("sendDebugMessage") when verbose logging is enabled
  -> Runtime.evaluate(the bundled mapper JavaScript)
  -> Runtime.evaluate(window.runMapperInstance(...), awaitPromise: true)
  -> Runtime.evaluate(onBidiMessage(... internal session.new ...)) and wait
  -> return the HTTP New Session response containing webSocketUrl
```

After startup, a client command follows this path:

```text
BiDi client WebSocket
  <-> ChromeDriver WebSocket server / BidiTracker
  <-> Runtime.evaluate(onBidiMessage(...)) in the hidden mapper target
  <-> JavaScript BiDi-to-CDP translation
  <-> window.cdp, injected by Target.exposeDevToolsProtocol
  <-> Chromium CDP instrumentation for pages/workers/browser
```

The mapper sends BiDi results and events back through the `sendBidiResponse`
runtime binding. CDP documents `Target.exposeDevToolsProtocol` as injecting an
object with `send(json)` and `onmessage` into the target:
[CDP Target domain](https://chromedevtools.github.io/devtools-protocol/tot/Target/#method-exposeDevToolsProtocol).

Chrome 150 embeds chromium-bidi 14.0.0 at revision
`6d0a494110fe0c47dcc75a1a4dfa110c25097827`:
[Chromium third-party metadata](https://chromium.googlesource.com/chromium/src/+/refs/branch-heads/7871/third_party/bidimapper/README.chromium).
The distributed `lib/iife/mapperTab.js` is 830,648 bytes. ChromeDriver injects
that string into every new BiDi session with `Runtime.evaluate`; it is not a
long-lived service shared by sessions.

## Measurement method

Environment:

- macOS 15.7.7, Darwin 24.6.0, x86_64
- Intel Core i7-4750HQ at 2.00 GHz
- Node 26.4.0
- headless unless noted
- raw HTTP/WebSocket and Node built-ins; no Selenium/Puppeteer/Playwright client

Browser pairs:

| artifact | browser | driver |
|---|---|---|
| installed Google Chrome | 150.0.7871.101 | 150.0.7871.115 |
| Homebrew Chromium snapshot | 152.0.7943.0 | 152.0.7942.0 |
| Chrome for Testing headless shell | 150.0.7871.115 | 150.0.7871.115 |

The Chrome Stable browser and driver share `MAJOR.MINOR.BUILD` and differ only
in patch. Chromium and its Canary driver share the major version but have
adjacent builds, so its numbers should be treated as a current-architecture
comparison, not a release-quality regression measurement.

BiDi and Classic capabilities differ only by `webSocketUrl: true`. Samples are
paired/interleaved. The detailed profiler correlates ChromeDriver verbose-log
command IDs with their responses and uses the actual `RESPONSE InitSession`
marker. Earlier versions of this repo incorrectly used the final log timestamp,
which included session teardown; that is now fixed and covered by a test.

### Fresh New Session

| browser | Classic median | BiDi median | difference of displayed medians | paired profiler penalty |
|---|---:|---:|---:|---:|
| Chrome Stable 150 | 1,749 ms | 2,241 ms | +492 ms | **+430 ms** |
| Chromium snapshot 152 | 2,015 ms | 2,378 ms | +363 ms | **+342 ms** |
| `chrome-headless-shell` 150 | 616 ms | 998 ms | +382 ms | **+401 ms** |

The displayed medians and profiler were separate runs, so their deltas need not
match. The paired profiler is the stronger estimate because it uses the median
of per-pair deltas.

Chromium had unrelated 8–9 second browser-launch outliers. Its post-boot paired
deltas were much steadier (`325 239 232 310 238` ms; median 239 ms), confirming
that the mapper tax remains while also showing why robust paired statistics are
needed. In that build, mapper hidden-renderer readiness was 95 ms and bundle
evaluation 52 ms, while initial target setup itself was 332 ms. A newer Chromium
snapshot did not provide a generally faster bootstrap on this machine.

### Chrome Stable mapper critical path

Five paired samples after one warm-up:

```text
New Session BiDi - Classic:  440 425 381 477 430 ms   median 430 ms
post-boot BiDi - Classic:    435 428 400 450 413 ms   median 428 ms
Classic post-boot baseline:   58  41  56  20  50 ms   median  50 ms
```

Median BiDi post-boot phases:

```text
initial target attach/setup (mostly common)      40 ms
BiDi-only initial about:blank navigation         25 ms
create + attach hidden mapper target             14 ms
wait for hidden mapper renderer readiness       266 ms
runtime/CDP bridge + bindings setup              15 ms
parse/evaluate bundled mapper JavaScript         61 ms
launch mapper instance                           29 ms
mapper internal BiDi session.new                 17 ms
```

The 266 ms renderer wait is visible directly in the log: commands such as
`Page.enable`, `Page.addScriptToEvaluateOnNewDocument`, and `Runtime.evaluate`
are issued to the new hidden target, then their responses arrive only after
`Page.frameStoppedLoading`. The result is consistent with ChromeDriver creating
and waiting for a new active page/renderer, not with a 266 ms BiDi protocol
operation.

## What is protocol-mandated and what is not

The current WebDriver BiDi specification says clients opt in by requesting
`webSocketUrl: true`; the New Session extension starts a WebSocket listener,
constructs the URL, and sets the session's BiDi flag. It does **not** require a
JavaScript mapper, CDP, a tab, a hidden renderer, or a particular startup delay:
[WebDriver BiDi §4.1](https://www.w3.org/TR/webdriver-bidi/#establishing-a-connection).

Therefore:

- The measured delay is a Chromium/ChromeDriver implementation limitation.
- It is not an unavoidable consequence of WebSocket transport or the BiDi data
  model.
- A W3C specification change cannot by itself remove Chrome's mapper target.
  The direct owner of the critical path is Chromium's ChromeDriver/BiDi
  implementation.

Firefox's native implementation remains a useful architectural control. The
existing repo results found no measurable Firefox BiDi New Session penalty, but
Firefox was not re-run in this investigation because Firefox/GeckoDriver were
not installed on this machine.

There is also an open upstream command-latency issue. Chromium maintainers state
that Chrome's BiDi implementation is based on CDP, cannot be faster than the CDP
foundation, and should be brought as close to raw CDP as possible:
[chromium-bidi issue #3974](https://github.com/GoogleChromeLabs/chromium-bidi/issues/3974),
[maintainer architecture comment](https://github.com/GoogleChromeLabs/chromium-bidi/issues/3974#issuecomment-3748807294).
That issue concerns steady-state command latency; this report identifies the
separate per-session bootstrap cost.

## Upstream performance gap

chromium-bidi now has an official performance dashboard and documents Puppeteer
BiDi-vs-CDP, Selenium BiDi/Classic/CDP, and E2E command benchmarks:

- [official dashboard](https://googlechromelabs.github.io/chromium-bidi/bench/)
- [benchmark methodology](https://github.com/GoogleChromeLabs/chromium-bidi/blob/main/docs/benchmark.md)

As of this date, its published metric names contain command/relative-overhead
metrics but no launch, New Session, mapper-startup, or session-creation metric.
The documented Selenium/Puppeteer methodology evaluates commands many times
after each launch. A mapper bootstrap regression can therefore be invisible to
the existing primary metric.

The most useful immediate upstream request is to add a paired
`POST /session` benchmark with and without `webSocketUrl: true`, plus internal
ChromeDriver phase telemetry. That makes this cost a continuously tracked
regression target rather than a one-off report.

## Optimization opportunities to take to Chromium and the WG

Ordered by the measured opportunity:

1. **Avoid a fresh page renderer for the mapper.** ChromeDriver currently says
   its BiDi server supports page clients only and even comments that another
   target type might be used later. A browser/utility/worker execution context,
   or a driver-side runtime, could attack the 62% dominant phase.
2. **Pre-warm or safely reuse the mapper environment.** Start it concurrently
   with common browser initialization, or pool it across sequential sessions
   with a rigorously specified reset. Session state, subscriptions, cached
   realms/navigables, permissions, and cleanup make reuse non-trivial.
3. **Cache or precompile the mapper bundle.** Injecting and compiling an 831 KB
   script costs about 61 ms here. A V8 startup snapshot, code cache, module
   resource, or compiled-in execution environment could reduce this slice.
4. **Parallelize independent initialization.** Initial-page normalization,
   mapper-target creation, runtime setup, and WebSocket listener setup should be
   audited for dependencies that force the current serial path.
5. **Consider returning New Session once the listener can safely queue.** The
   implementation could accept/queue commands while mapper initialization
   completes. This needs careful spec and race analysis; it moves latency from
   HTTP New Session to the first real command unless pre-warming overlaps useful
   client work.
6. **Add trace markers and a startup benchmark upstream.** Suggested markers:
   first CDP ready, initial target ready, hidden target created, hidden renderer
   ready, bundle evaluated, mapper instance ready, internal `session.new` ready,
   HTTP New Session returned.

A useful distinction for WG discussion: Chrome may continue to use CDP as its
foundational instrumentation without requiring the BiDi protocol router itself
to live in a new page renderer. “CDP remains foundational” does not imply that
the current per-session hidden-tab bootstrap is a permanent lower bound.

## What can be made faster today

### 1. Use `chrome-headless-shell` when its fidelity is sufficient

On this machine it reduced fresh BiDi startup from roughly 2.24 s to 1.00 s.
The mapper still cost about 0.4 s, but browser boot was much smaller.
`browsingContext.getTree/create/close` and
`browser.createUserContext/removeUserContext` were also exercised successfully,
so this was not merely capability negotiation.

Chrome documents the trade-off clearly: headless shell is a lightweight wrapper
around Chromium `//content` with fewer dependencies and can be more performant;
new headless is the real Chrome browser and is more authentic, reliable, and
feature-complete:
[Chrome headless-shell guidance](https://developer.chrome.com/blog/chrome-headless-shell).

Use headless shell for tests that do not depend on full Chrome UI, extensions,
or other `//chrome` features. Keep a representative full-Chrome lane for
high-fidelity coverage.

### 2. Reuse one BiDi session and create user contexts

The new `bench/reuse-session.mjs` measured:

| ready-to-use context | Chrome 150 median | Chromium 152 median |
|---|---:|---:|
| new tab in existing profile | 172 ms | 191 ms |
| isolated user context plus tab | 406 ms | 515 ms |

WebDriver BiDi standardizes `browser.createUserContext`,
`browsingContext.create`, and `browser.removeUserContext`; removal closes all
navigables in that context without `beforeunload`:
[WebDriver BiDi browser user contexts](https://www.w3.org/TR/webdriver-bidi/#browser-module),
[browsingContext.create](https://www.w3.org/TR/webdriver-bidi/#command-browsingContext-create).

This can isolate cookies and site storage and allows per-context proxy,
certificate, and prompt settings in the current specification. It does not
provide a new browser process, fresh process-global flags, or perfect isolation
from all browser-global state. Whether it is acceptable is a test-model choice.

### 3. Keep a warm browser pool

If every test truly needs process isolation, pre-launch a bounded pool of BiDi
browsers before tests need them. This does not reduce CPU time or the individual
critical path, but overlaps it with other work. The cost is memory and more
complex lifecycle/crash handling.

ChromeDriver can also attach to an existing browser using `debuggerAddress`,
but this has product limitations: Chrome documents that some commands are
unsupported because its automation extension is loaded only when ChromeDriver
itself launches Chrome:
[remote-debugging limitations](https://developer.chrome.com/docs/chromedriver/help/operation-not-supported-when-using-remote-debugging).
It was not included as a recommended or measured primary path here.

There is no supported way to start a Chrome Classic WebDriver session and turn
it into a WebDriver BiDi session later. `webSocketUrl` is a New Session opt-in,
so deferring the decision does not avoid a new session.

## Concise proposal for the Browser Testing and Tools WG / Chromium team

> Requesting `webSocketUrl: true` in Chrome 150 adds a repeatable ~430 ms to New
> Session on the measured Intel Mac. ChromeDriver verbose-log correlation shows
> that ~62% of the BiDi-only path is waiting for the dedicated hidden mapper
> renderer and ~14% is evaluating the 831 KB mapper bundle. The WebDriver BiDi
> connection algorithm requires a listener and BiDi session flag, not a mapper
> tab, so this is implementation-specific. Please add New Session mapper startup
> to the official chromium-bidi performance dashboard and investigate a
> non-page, reusable/pre-warmed, or precompiled mapper execution environment.
> Optimizing mapper command translation alone cannot address the dominant
> startup phase.
